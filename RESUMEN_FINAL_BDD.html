3 · Teoría: bases de datos y modelos

  • Base de datos: conjunto de datos organizados y relacionados, almacenados de forma que se puedan consultar y modificar. El programa que la gestiona es el SGBD / DBMS (ej. MySQL).
  • Ventajas vs archivos sueltos: evita redundancia, mantiene la integridad, permite acceso concurrente y controla la seguridad.
  • Los 3 modelos (niveles de abstracción):
    • Conceptual → el DER (independiente del motor).
    • Lógico → el modelo relacional (tablas, PK, FK).
    • Físico → cómo se guarda realmente en disco.
ACID (propiedades de una transacción): Atomicidad (todo o nada), Consistencia (respeta las reglas), Aislamiento (Isolation, no se pisan entre sí) y Durabilidad (una vez confirmada, persiste).

Álgebra relacional (por si cae teoría)

  • Selección (σ): elige filas que cumplen una condición → equivale a WHERE.
  • Proyección (π): elige columnas → equivale a poner columnas en el SELECT.
  • Producto cartesiano (×) y Join (⋈): combinan tablas.
  • Unión, Intersección, Diferencia: operaciones entre conjuntos de filas.

4 · Diagrama Entidad-Relación (DER) 🎯 el 60%

Conceptos base

  • Entidad: un concepto del mundo real que guardamos (Cliente, Producto, Venta). Se dibuja como una tabla/rectángulo.
  • Atributo: una característica de la entidad (nombre, precio, DNI).
  • Clave primaria (PK): atributo que identifica de forma única cada fila (normalmente id_... autoincremental).
  • Clave foránea (FK): la PK de otra entidad copiada como atributo, para relacionar dos tablas.
  • Relación: el vínculo entre entidades (un cliente realiza ventas).
  • Cardinalidad: cuántos de un lado se vinculan con cuántos del otro.

Los 3 tipos de cardinalidad

TipoEjemploCómo se resuelve
1:1 uno a unoPersona ↔ DNILa FK va en cualquiera de las dos tablas.
1:N uno a muchosCliente → VentasLa FK va del lado N (el "muchos").
N:M muchos a muchosVenta ↔ ProductoSe crea una tabla intermedia con las 2 FK.
🔑 Regla de oro de la FK (1:N): "La FK vive en el lado de los muchos, apuntando al lado del uno." Un cliente tiene muchas ventas → cada venta guarda id_cliente. (Nunca al revés: no podés meter muchos id_venta en un cliente.)
⚠️ La trampa que más se cobra — N:M: cuando ambos lados pueden tener varios del otro, NO va una FK suelta. Va una tabla intermedia. Y esa tabla suele llevar atributos propios (cantidad, fecha, nota, monto...).

Señal de alarma: las palabras "varios / múltiples / uno o más" en las dos direcciones = N:M seguro.

Caso especial: relación entre una entidad y sí misma / participantes fijos

Cuando algo relaciona a una entidad con otra del mismo tipo, en cantidad fija (ej. una partida enfrenta a 2 equipos), no se usa tabla intermedia: se ponen 2 FK con nombres de rol distintos apuntando a la misma tabla.

PARTIDA (id_partida PK, fecha, resultado,
         id_equipo_local     FK -> EQUIPO,
         id_equipo_visitante FK -> EQUIPO)

Cantidad fija (siempre 2) → varias FK con roles. Cantidad variable (muchos) → tabla intermedia N:M.

Los 6 pasos para pasar de enunciado a DER

  1. Subrayá los sustantivos importantes del enunciado → candidatos a entidades.
  2. Para cada entidad, listá sus atributos (lo que "se guarda de...") y elegí su PK.
  3. Buscá los verbos que conectan entidades → son las relaciones.
  4. Definí la cardinalidad de cada relación (preguntá "¿cuántos de A por cada B y viceversa?").
  5. Colocá las FK: 1:N → FK del lado N. N:M → tabla intermedia.
  6. Revisá que cada dato del enunciado tenga dónde guardarse.

Mini-ejercicios de modelado media

a) "Un autor escribe muchos libros y cada libro tiene un solo autor." ¿Tipo y dónde va la FK?

Ver respuesta

1:N. La FK id_autor va en LIBROS (lado muchos).

b) "Un alumno cursa varias materias y una materia tiene varios alumnos; se registra la nota final de cada alumno en cada materia." ¿Cómo lo modelás?

Ver respuesta

N:M → tabla intermedia CURSADA (id PK, id_alumno FK, id_materia FK, nota_final). La nota_final es atributo propio de la intermedia (no del alumno ni de la materia).

c) final "Un pedido puede incluir uno o más productos y cada producto aparece en muchos pedidos; de cada producto en el pedido se guarda la cantidad." Modelalo completo.

Ver respuesta 
PEDIDOS   (id_pedido PK, fecha, id_cliente FK)
PRODUCTOS (id_producto PK, nombre, precio)
DETALLE_PEDIDO (id_detalle PK, id_pedido FK,
                id_producto FK, cantidad)

"uno o más productos" + "muchos pedidos" = N:M → intermedia DETALLE_PEDIDO con cantidad propia.

5 · Pasaje DER → Modelo Relacional

Reglas mecánicas para convertir el diagrama en tablas:

  • Cada entidad → una tabla. Sus atributos → columnas. Su identificador → PK.
  • Relación 1:N → se agrega la FK del lado 1 en la tabla del lado N (no se crea tabla nueva).
  • Relación N:M → se crea una tabla intermedia nueva con las 2 FK (+ sus atributos).
  • Relación 1:1 → FK en cualquiera de las dos (elegí la que tenga sentido).

Notación al escribir la estructura (así queda claro y prolijo):

TABLA (PK, atributo, atributo, FK -> tabla_referenciada)
Tip de examen: si el profe pide "estructura de base de datos", cada tabla tiene que tener su PK marcada y sus FK indicadas. Podés agregar el tipo de dato (INT, VARCHAR, DATE, DECIMAL) para sumar.

6 · Normalización

Es el proceso de organizar las tablas para eliminar redundancia y evitar anomalías al insertar, modificar o borrar. Se avanza por formas normales, cada una exige cumplir la anterior.

Primera Forma Normal (1FN)

  • Todos los atributos son atómicos (un solo valor por celda, nada de "listas" en un campo).
  • No hay grupos repetidos (ej. tel1, tel2, tel3 → mal).
  • Cada tabla tiene PK.
Mal (viola 1FN): CLIENTE(id, nombre, telefonos="221-555, 223-777") → dos teléfonos en una celda.
Bien: tabla aparte TELEFONOS(id, id_cliente FK, numero).

Segunda Forma Normal (2FN)

  • Está en 1FN y todos los atributos no clave dependen de toda la PK, no de una parte.
  • Solo es riesgo cuando la PK es compuesta (dos o más columnas).
Mal: DETALLE(id_venta, id_producto, cantidad, nombre_producto) → nombre_producto depende solo de id_producto (parte de la clave), no de toda la PK.
Bien: mover nombre_producto a la tabla PRODUCTOS.

Tercera Forma Normal (3FN)

  • Está en 2FN y no hay dependencias transitivas: ningún atributo no clave depende de otro atributo no clave.
Mal: PRODUCTO(id_producto, nombre, id_categoria, nombre_categoria) → nombre_categoria depende de id_categoria, no de la PK del producto.
Bien: nombre_categoria va en la tabla CATEGORIAS.
Frase para recordar (3FN): "cada atributo depende de la clave, toda la clave, y nada más que la clave."

7 · Integridad referencial y restricciones

La cátedra toma preguntas de CREATE TABLE con restricciones y "¿qué pasa si ejecuto...?". Repasá esto.

Restricciones (constraints)

  • PRIMARY KEY: identifica única cada fila, no admite NULL ni repetidos.
  • FOREIGN KEY: obliga a que el valor exista en la tabla referenciada (integridad referencial).
  • NOT NULL: el campo no puede quedar vacío.
  • UNIQUE: no se puede repetir el valor (pero sí admite NULL).
  • CHECK: condición que debe cumplir el dato (ej. CHECK (stock > 0)).
  • AUTO_INCREMENT: genera el número solo, sirve para PK.
CREATE TABLE productos (
  id_producto INT AUTO_INCREMENT,
  nombre VARCHAR(50) NOT NULL,
  precio FLOAT NOT NULL,
  id_categoria INT,
  CONSTRAINT pk_productos PRIMARY KEY (id_producto),
  CONSTRAINT fk_categoria FOREIGN KEY (id_categoria)
     REFERENCES categorias(id_categoria) ON DELETE NO ACTION
);

Acciones al borrar/actualizar el padre (ON DELETE)

AcciónQué hace al borrar el registro "padre"
NO ACTION / RESTRICTNo deja borrar si hay hijos que lo referencian (error).
CASCADEBorra también los hijos automáticamente (efecto dominó).
SET NULLPone la FK de los hijos en NULL.
Pregunta típica: "Si borro un producto y la FK en STOCK tiene ON DELETE CASCADE, ¿qué pasa?" → se borra el producto y todos sus registros en STOCK.

8 · SELECT, WHERE, ORDER BY

Estructura básica de una consulta (DQL):

SELECT columnas
FROM tabla
WHERE condicion
ORDER BY columna [ASC | DESC];

Operadores útiles en el WHERE

= <> > < >= <= AND / OR / NOT BETWEEN a AND b IN (v1, v2) LIKE '%texto%' IS NULL / IS NOT NULL
Fechas: se comparan como texto con formato 'AAAA-MM-DD'. YEAR(fecha), MONTH(fecha), DAY(fecha) extraen partes. CURDATE() = hoy. BETWEEN '2024-01-01' AND '2024-06-30' para un rango.

Ejercicios

fácil Listar nombre y precio de los productos con precio mayor a 800.

Ver solución 
SELECT nombre, precio FROM productos
WHERE precio > 800;

fácil Clientes de 'Mar del Plata', ordenados por nombre.

Ver solución 
SELECT * FROM clientes
WHERE ciudad = 'Mar del Plata'
ORDER BY nombre;

media Productos con precio entre 600 y 1200, de la categoría 1, ordenados de mayor a menor precio.

Ver solución 
SELECT nombre, precio FROM productos
WHERE precio BETWEEN 600 AND 1200
  AND id_categoria = 1
ORDER BY precio DESC;

media Clientes que NO tienen email cargado.

Ver solución 
SELECT * FROM clientes
WHERE email IS NULL;

Ojo: = NULL NO funciona, siempre IS NULL.

9 · GROUP BY, HAVING y funciones de agregado

GROUP BY agrupa filas que comparten un valor, para aplicarles una función de agregado por grupo.

Funciones de agregado

COUNT(*) cantidad SUM(col) suma AVG(col) promedio MAX(col) mayor MIN(col) menor 
SELECT columna_grupo, FUNCION(col)
FROM tabla
WHERE   -- filtra filas ANTES de agrupar
GROUP BY columna_grupo
HAVING  -- filtra GRUPOS ya formados (usa agregados)
ORDER BY ...;
⚠️ WHERE vs HAVING — la diferencia que toman siempre:
• WHERE filtra filas individuales, antes de agrupar. No puede usar SUM, COUNT, etc.
• HAVING filtra grupos, después de agrupar. Sí puede usar funciones de agregado.
"Mostrame las categorías con más de 5 productos" → eso es un HAVING COUNT(*) > 5.
Regla del SELECT: toda columna del SELECT que no esté dentro de una función de agregado debe estar en el GROUP BY.
Orden de ejecución real (no el de escritura):
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT

Ejercicios

fácil ¿Cuántos productos hay en total?

Ver solución 
SELECT COUNT(*) FROM productos;

media Cantidad de productos por categoría.

Ver solución 
SELECT id_categoria, COUNT(*) AS cantidad
FROM productos
GROUP BY id_categoria;

media Precio promedio de productos por categoría, pero solo contando productos con stock mayor a 0.

Ver solución 
SELECT id_categoria, AVG(precio) AS precio_prom
FROM productos
WHERE stock > 0
GROUP BY id_categoria;

El filtro de stock es por fila → va en WHERE.

difícil Categorías que tienen más de 1 producto.

Ver solución 
SELECT id_categoria, COUNT(*) AS cantidad
FROM productos
GROUP BY id_categoria
HAVING COUNT(*) > 1;

"Grupos con más de 1" → condición sobre el COUNT → HAVING.

final Por cada venta, mostrar el id_venta y el total facturado (cantidad × precio_unitario sumado), solo de las ventas cuyo total supere 2000.

Ver solución 
SELECT id_venta, SUM(cantidad * precio_unitario) AS total
FROM detalle_venta
GROUP BY id_venta
HAVING SUM(cantidad * precio_unitario) > 2000;

10 · JOINs (apareamiento de tablas)

Un JOIN combina filas de dos o más tablas relacionadas por su PK–FK. Se usa cuando necesitás datos que están en tablas distintas (ej. el nombre del cliente que está en CLIENTES, junto con la fecha de la venta que está en VENTAS).

TipoQué devuelveCuándo
INNER JOINSolo las filas con coincidencia en ambas tablas.El más común. "Clientes que tienen ventas".
LEFT JOINTodo lo de la tabla izquierda + lo que coincida de la derecha (NULL si no hay)."Todos los clientes, tengan o no ventas".
RIGHT JOINTodo lo de la derecha + lo que coincida de la izquierda."Todas las ventas, tengan o no cliente".

Sintaxis (con alias, recomendado)

SELECT c.nombre, v.fecha
FROM clientes c
INNER JOIN ventas v ON c.id_cliente = v.id_cliente;
La clave de todo JOIN es el ON: ahí decís por qué campos se relacionan las tablas (siempre PK = FK). Si te olvidás el ON, se arma un producto cartesiano (todas las filas contra todas — error).

Ejercicios

fácil Mostrar el nombre de cada producto junto al nombre de su categoría.

Ver solución 
SELECT p.nombre, cat.nombre AS categoria
FROM productos p
INNER JOIN categorias cat ON p.id_categoria = cat.id_categoria;

media Mostrar cada venta con el nombre y la ciudad del cliente que la hizo.

Ver solución 
SELECT v.id_venta, v.fecha, c.nombre, c.ciudad
FROM ventas v
INNER JOIN clientes c ON v.id_cliente = c.id_cliente;

media Mostrar todos los clientes y, si tienen, sus ventas (los que no tienen, igual aparecen).

Ver solución 
SELECT c.nombre, v.id_venta
FROM clientes c
LEFT JOIN ventas v ON c.id_cliente = v.id_cliente;

LEFT JOIN → aparece Caro aunque no tenga ventas (id_venta = NULL).

difícil Total facturado por cada cliente (nombre + suma de cantidad×precio de sus detalles). Une 3 tablas + GROUP BY.

Ver solución 
SELECT c.nombre, SUM(d.cantidad * d.precio_unitario) AS total
FROM clientes c
INNER JOIN ventas v ON c.id_cliente = v.id_cliente
INNER JOIN detalle_venta d ON v.id_venta = d.id_venta
GROUP BY c.nombre;

final Nombre de cada producto y la cantidad total vendida de cada uno, ordenado de más vendido a menos.

Ver solución 
SELECT p.nombre, SUM(d.cantidad) AS total_vendido
FROM productos p
INNER JOIN detalle_venta d ON p.id_producto = d.id_producto
GROUP BY p.nombre
ORDER BY total_vendido DESC;

11 · Subconsultas bloque 2 del final (SIN JOIN)

Una subconsulta es una consulta dentro de otra. La de adentro se ejecuta primero y su resultado lo usa la de afuera. Va siempre entre paréntesis.

🔑 La regla del = vs IN:
• Si la subconsulta devuelve UN solo valor → = (o >, <).
• Si puede devolver varias filas → IN.
Usar = con una subconsulta que devuelve varias filas = error. Ante la duda, IN es más seguro.

Tipo 1 — devuelve un valor (con agregado)

fácil Productos más caros que el precio promedio.

Ver solución 
SELECT nombre, precio FROM productos
WHERE precio > (SELECT AVG(precio) FROM productos);

media Todos los datos del producto más caro.

Ver solución 
SELECT * FROM productos
WHERE precio = (SELECT MAX(precio) FROM productos);

Compará columna con columna: precio = MAX(precio). No mezcles id con precio.

Tipo 2 — devuelve una lista (con IN)

media Nombres de los productos de la categoría 'Bebidas' (sin JOIN).

Ver solución 
SELECT nombre FROM productos
WHERE id_categoria IN (
   SELECT id_categoria FROM categorias
   WHERE nombre = 'Bebidas');

La subconsulta necesita su propio FROM.

Tipo 3 — anidadas (subconsulta dentro de subconsulta)

difícil Datos del cliente que hizo la venta con id más alto (pensalo en capas).

Ver solución 
SELECT * FROM clientes
WHERE id_cliente IN (
   SELECT id_cliente FROM ventas
   WHERE id_venta = (SELECT MAX(id_venta) FROM ventas)
);

Como muñecas rusas: cada (...) se resuelve primero y le pasa el valor a la de afuera.

final Nombre de los productos vendidos en la venta de id 1 (atravesando la tabla intermedia, sin JOIN).

Ver solución 
SELECT nombre FROM productos
WHERE id_producto IN (
   SELECT id_producto FROM detalle_venta
   WHERE id_venta = 1);

Tipo 4 — correlacionada (con COUNT / SUM por fila)

La subconsulta "mira" un dato de la consulta de afuera. Sirve para "¿cuántos X tiene cada Y?".

final Categorías que tienen exactamente 2 productos (sin JOIN).

Ver solución 
SELECT * FROM categorias c
WHERE (SELECT COUNT(*) FROM productos p
       WHERE p.id_categoria = c.id_categoria) = 2;

La línea p.id_categoria = c.id_categoria conecta adentro con afuera.

final Clientes cuyo total de ventas (cantidad de ventas) sea mayor a 1.

Ver solución 
SELECT * FROM clientes cl
WHERE (SELECT COUNT(*) FROM ventas v
       WHERE v.id_cliente = cl.id_cliente) > 1;
⚠️ No olvides la comparación final: toda subconsulta en un WHERE termina en un operador (=, >, IN...). Si escribís WHERE (SELECT ...) y ahí corta, falta el > 1 o lo que sea.

12 · Procedimientos almacenados bloque 3 (se puede JOIN)

Un SP es un bloque de código SQL guardado en la BD, que se ejecuta con CALL y puede recibir parámetros.

Esqueleto base — memorizalo

DELIMITER $$

CREATE PROCEDURE nombre_sp(IN p_param INT)
BEGIN
   -- cuerpo
END $$

DELIMITER ;

CALL nombre_sp(5);
Piezas clave: DELIMITER $$ (cambia el fin de línea para poder usar ; adentro), BEGIN ... END (el cuerpo), parámetros con IN, y al final DELIMITER ; para volver a la normalidad.

Los 3 patrones básicos

-- UPDATE con filtro
UPDATE tabla SET col = valor WHERE id = p_id;

-- INSERT (siempre listá las columnas)
INSERT INTO tabla (c1, c2) VALUES (p_1, p_2);

-- SELECT calculado (con AS, nunca con =)
SELECT monto, monto * p_porc/100 AS comision
FROM ventas WHERE id_venta = p_id;
⚠️ = es de UPDATE, AS es de SELECT. En un SELECT, para nombrar un cálculo se usa expresión AS alias, nunca columna = valor. El col = valor es solo del SET del UPDATE.

Variables e IF

DECLARE v_x INT;                    -- al inicio del BEGIN
SELECT col INTO v_x FROM ... ;      -- guarda un valor en la variable

IF condicion THEN
   ...
ELSEIF otra_condicion THEN       -- ELSEIF junto, y SIEMPRE con condición + THEN
   ...
ELSE
   ...
END IF;

Patrón "¿existe?"

DECLARE v_cant INT;
SELECT COUNT(*) INTO v_cant FROM productos WHERE id_producto = p_id;
IF v_cant > 0 THEN
   -- existe
ELSE
   SELECT 'No existe' AS mensaje;
END IF;

Ejercicios

fácil SP buscar_producto(p_id): devolver todos los datos de ese producto.

Ver solución 
DELIMITER $$
CREATE PROCEDURE buscar_producto(IN p_id INT)
BEGIN
   SELECT * FROM productos WHERE id_producto = p_id;
END $$
DELIMITER ;

media SP aplicar_descuento(p_id, p_porc): bajar el precio del producto en ese porcentaje.

Ver solución 
DELIMITER $$
CREATE PROCEDURE aplicar_descuento(IN p_id INT, IN p_porc DECIMAL(5,2))
BEGIN
   UPDATE productos
   SET precio = precio * (1 - p_porc/100)
   WHERE id_producto = p_id;
END $$
DELIMITER ;

Porcentaje = valor * (1 ± porc/100). Descuento resta, aumento suma.

difícil SP clasificar_stock(p_id): si stock > 30 mostrar 'Stock alto', si no 'Stock bajo'.

Ver solución 
DELIMITER $$
CREATE PROCEDURE clasificar_stock(IN p_id INT)
BEGIN
   DECLARE v_stock INT;
   SELECT stock INTO v_stock FROM productos WHERE id_producto = p_id;
   IF v_stock > 30 THEN
      SELECT 'Stock alto' AS mensaje;
   ELSE
      SELECT 'Stock bajo' AS mensaje;
   END IF;
END $$
DELIMITER ;

final SP actualizar_precio(p_id, p_nuevo): si el producto existe, actualizar su precio; si el nuevo precio es mayor al viejo poner categoría en la 1, si es menor en la 2, si es igual no tocar la categoría. Si no existe, avisar. (Patrón completo: existencia + guardar valor viejo + IF/ELSEIF/ELSE.)

Ver solución 
DELIMITER $$
CREATE PROCEDURE actualizar_precio(IN p_id INT, IN p_nuevo DECIMAL(10,2))
BEGIN
   DECLARE v_cant INT;
   DECLARE v_viejo DECIMAL(10,2);

   SELECT COUNT(*) INTO v_cant FROM productos WHERE id_producto = p_id;

   IF v_cant > 0 THEN
      SELECT precio INTO v_viejo FROM productos WHERE id_producto = p_id;

      IF p_nuevo > v_viejo THEN
         UPDATE productos SET precio = p_nuevo, id_categoria = 1 WHERE id_producto = p_id;
      ELSEIF p_nuevo < v_viejo THEN
         UPDATE productos SET precio = p_nuevo, id_categoria = 2 WHERE id_producto = p_id;
      ELSE
         UPDATE productos SET precio = p_nuevo WHERE id_producto = p_id;
      END IF;
   ELSE
      SELECT 'El producto no existe' AS mensaje;
   END IF;
END $$
DELIMITER ;
