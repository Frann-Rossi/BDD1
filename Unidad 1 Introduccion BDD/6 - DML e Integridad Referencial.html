Unidad 1 · Parte 6 · Manipulación de datos

DML e integridad referencial

Las tablas ya existen. Ahora vas a aprender a cargar, corregir y eliminar filas sin romper las reglas del modelo. El objetivo no es memorizar tres comandos: es comprender qué cambia cada sentencia, qué restricciones intervienen y cómo trabajar sin modificar datos por accidente.

Nivel inicialMySQL 8Lectura autónomaPráctica segura

Al finalizar vas a poder

  • Agregar una o varias filas con INSERT.
  • Modificar datos existentes con UPDATE y una condición precisa.
  • Eliminar filas con DELETE sin confundirlo con TRUNCATE o DROP.
  • Interpretar errores producidos por PK, FK, UNIQUE, NOT NULL y CHECK.
  • Comprender cómo actúan RESTRICT, CASCADE y SET NULL.
  • Usar una transacción básica para probar cambios reversibles.

02 · Punto de partida reproducible

Preparar la práctica

Los ejemplos utilizan la base gestion_academica. Si ya ejecutaste el script de la Parte 5, podés continuar. Si necesitás reconstruir el escenario, este script mínimo crea cinco tablas relacionadas.

Mostrar script base completo 
CREATE DATABASE IF NOT EXISTS gestion_academica
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_0900_ai_ci;

USE gestion_academica;

CREATE TABLE carreras (
    id_carrera INT UNSIGNED AUTO_INCREMENT,
    nombre VARCHAR(100) NOT NULL,
    duracion_anios TINYINT UNSIGNED NOT NULL,
    estado ENUM('Activa', 'Inactiva') NOT NULL DEFAULT 'Activa',
    CONSTRAINT pk_carreras PRIMARY KEY (id_carrera),
    CONSTRAINT uq_carreras_nombre UNIQUE (nombre),
    CONSTRAINT chk_carreras_duracion CHECK (duracion_anios BETWEEN 1 AND 8)
) ENGINE = InnoDB;

CREATE TABLE materias (
    id_materia INT UNSIGNED AUTO_INCREMENT,
    nombre VARCHAR(100) NOT NULL,
    carga_horaria SMALLINT UNSIGNED NOT NULL,
    CONSTRAINT pk_materias PRIMARY KEY (id_materia),
    CONSTRAINT uq_materias_nombre UNIQUE (nombre),
    CONSTRAINT chk_materias_carga CHECK (carga_horaria BETWEEN 16 AND 300)
) ENGINE = InnoDB;

CREATE TABLE alumnos (
    id_alumno BIGINT UNSIGNED AUTO_INCREMENT,
    legajo VARCHAR(20) NOT NULL,
    dni VARCHAR(15) NOT NULL,
    apellido VARCHAR(60) NOT NULL,
    nombre VARCHAR(60) NOT NULL,
    fecha_nacimiento DATE NULL,
    email VARCHAR(120) NULL,
    id_carrera INT UNSIGNED NOT NULL,
    CONSTRAINT pk_alumnos PRIMARY KEY (id_alumno),
    CONSTRAINT uq_alumnos_legajo UNIQUE (legajo),
    CONSTRAINT uq_alumnos_dni UNIQUE (dni),
    CONSTRAINT uq_alumnos_email UNIQUE (email),
    CONSTRAINT fk_alumnos_carreras
        FOREIGN KEY (id_carrera) REFERENCES carreras (id_carrera)
        ON UPDATE CASCADE ON DELETE RESTRICT
) ENGINE = InnoDB;

CREATE TABLE comisiones (
    id_comision INT UNSIGNED AUTO_INCREMENT,
    id_materia INT UNSIGNED NOT NULL,
    anio SMALLINT UNSIGNED NOT NULL,
    cuatrimestre TINYINT UNSIGNED NOT NULL,
    turno ENUM('Mañana', 'Tarde', 'Noche') NOT NULL,
    CONSTRAINT pk_comisiones PRIMARY KEY (id_comision),
    CONSTRAINT fk_comisiones_materias
        FOREIGN KEY (id_materia) REFERENCES materias (id_materia)
        ON UPDATE CASCADE ON DELETE RESTRICT,
    CONSTRAINT chk_comisiones_cuatrimestre CHECK (cuatrimestre IN (1, 2))
) ENGINE = InnoDB;

CREATE TABLE inscripciones (
    id_inscripcion BIGINT UNSIGNED AUTO_INCREMENT,
    id_alumno BIGINT UNSIGNED NOT NULL,
    id_comision INT UNSIGNED NOT NULL,
    fecha_inscripcion DATE NOT NULL,
    estado ENUM('Activa', 'Baja', 'Aprobada') NOT NULL DEFAULT 'Activa',
    CONSTRAINT pk_inscripciones PRIMARY KEY (id_inscripcion),
    CONSTRAINT uq_inscripciones_alumno_comision UNIQUE (id_alumno, id_comision),
    CONSTRAINT fk_inscripciones_alumnos
        FOREIGN KEY (id_alumno) REFERENCES alumnos (id_alumno)
        ON UPDATE CASCADE ON DELETE RESTRICT,
    CONSTRAINT fk_inscripciones_comisiones
        FOREIGN KEY (id_comision) REFERENCES comisiones (id_comision)
        ON UPDATE CASCADE ON DELETE RESTRICT
) ENGINE = InnoDB;
No ejecutes el script de creación sobre tablas que ya contienen trabajo importante. Antes de recrear estructuras, confirmar qué objetos existen y conservar una copia de los datos.

03 · Crear filas

INSERT: agregar datos

La forma más clara de insertar una fila es nombrar explícitamente las columnas y luego proporcionar sus valores en el mismo orden.

INSERT INTO carreras (nombre, duracion_anios)
VALUES ('Tecnicatura Universitaria en Programación', 2);

Tabla destino

carreras

Columnas

nombre y duracion_anios

Valores

Uno por cada columna, en el mismo orden.

No se incluyó id_carrera porque es AUTO_INCREMENT. Tampoco se indicó estado, por lo que MySQL utiliza su valor DEFAULT: 'Activa'.

INSERT INTO alumnos
    (legajo, dni, apellido, nombre, fecha_nacimiento, email, id_carrera)
VALUES
    ('A-1001', '45111222', 'Gómez', 'Lucía', '2005-08-17',
     'lucia.gomez@ejemplo.edu.ar', 1);
Buena práctica: escribir siempre la lista de columnas. Una sentencia como INSERT INTO alumnos VALUES (...) depende del orden físico de todas las columnas y se vuelve frágil si la estructura cambia.
¿Cómo puedo conocer el ID generado?
Después de un INSERT que generó un valor AUTO_INCREMENT, MySQL permite consultar SELECT LAST_INSERT_ID();. En una inserción múltiple devuelve el primer ID generado por esa sentencia.
04 · Variantes útiles de INSERT

Varias filas, DEFAULT y NULL

Insertar varias filas en una sola sentencia

INSERT INTO materias (nombre, carga_horaria)
VALUES
    ('Programación I', 128),
    ('Base de Datos I', 128),
    ('Matemática', 96);

Cada paréntesis representa una fila. La cantidad y el orden de valores deben coincidir con la lista de columnas.

Usar DEFAULT de forma explícita

INSERT INTO carreras (nombre, duracion_anios, estado)
VALUES ('Carrera de prueba', 3, DEFAULT);

Guardar un dato desconocido con NULL

INSERT INTO alumnos
    (legajo, dni, apellido, nombre, fecha_nacimiento, email, id_carrera)
VALUES
    ('A-1002', '45999888', 'Pérez', 'Martín', NULL, NULL, 1);
Omitir una columnaMySQL usa su DEFAULT, genera el valor automático o intenta guardar NULL según la definición.
Escribir NULLSignifica que el valor no está disponible. Solo funciona si la columna admite NULL.
Cadena vacía ''Es un texto conocido de longitud cero. No equivale a NULL.
Valor 0Es un número real. No significa automáticamente “sin dato”.
05 · Las relaciones imponen una secuencia

Orden correcto para cargar tablas relacionadas

Una clave foránea solo puede guardar un valor que ya exista en la tabla referenciada. Por eso se cargan primero las tablas independientes y después las dependientes.

1 · Tablas padrecarreras y materias
→
2 · Tablas hijasalumnos y comisiones
→
3 · Tabla asociativainscripciones
-- 1. Ya existen la carrera y la materia.
INSERT INTO carreras (nombre, duracion_anios)
VALUES ('Analista de Sistemas', 3);

INSERT INTO materias (nombre, carga_horaria)
VALUES ('Algoritmos I', 128);

-- 2. Se crean alumno y comisión usando IDs existentes.
INSERT INTO alumnos
    (legajo, dni, apellido, nombre, id_carrera)
VALUES ('A-1003', '44777111', 'López', 'Sofía', 1);

INSERT INTO comisiones
    (id_materia, anio, cuatrimestre, turno)
VALUES (1, 2026, 1, 'Noche');

-- 3. Recién ahora puede crearse la inscripción.
INSERT INTO inscripciones
    (id_alumno, id_comision, fecha_inscripcion)
VALUES (1, 1, '2026-03-10');
No adivinar IDs. En una práctica pequeña pueden verse fácilmente, pero en una aplicación real se recupera el ID generado o se consulta el registro correspondiente antes de crear la relación.
06 · Un error también puede ser una defensa

Restricciones que protegen los datos

Cuando una operación viola una regla, MySQL la rechaza. El mensaje puede parecer incómodo, pero indica que la base está evitando una inconsistencia.

IntentoRestricciónPor qué falla
Repetir un legajoUNIQUEEl legajo debe identificar a una sola persona.
Guardar apellido en NULLNOT NULLLa columna exige un valor.
Usar una carrera inexistenteFOREIGN KEYLa fila hija no puede apuntar a un padre inexistente.
Duración igual a 20 añosCHECKEl valor queda fuera del rango permitido.
Repetir alumno y comisiónUNIQUE compuestoLa misma inscripción no puede duplicarse.
 
-- Este INSERT debe fallar si no existe id_carrera = 9999.
INSERT INTO alumnos
    (legajo, dni, apellido, nombre, id_carrera)
VALUES ('A-9999', '40000000', 'Prueba', 'Error FK', 9999);
Leer el error con método: identificar la tabla, la restricción mencionada y el dato que intentaba violarla. No conviene desactivar una restricción para “hacer funcionar” una carga incorrecta.
07 · Cambiar filas existentes

UPDATE: modificar datos

UPDATE selecciona una tabla, indica las nuevas asignaciones con SET y utiliza WHERE para decidir qué filas se modifican.

UPDATE alumnos
SET email = 'lucia.gomez@utn.edu.ar'
WHERE id_alumno = 1;

Modificar varias columnas

UPDATE alumnos
SET apellido = 'Gómez Díaz',
    email = 'lucia.gomez.diaz@utn.edu.ar'
WHERE id_alumno = 1;

Modificar varias filas de manera intencional

UPDATE carreras
SET estado = 'Inactiva'
WHERE nombre = 'Carrera de prueba';
UPDATE sin WHERE: modifica todas las filas de la tabla. Puede ser válido en un caso excepcional, pero nunca debe ocurrir por olvido.
-- PELIGRO: modifica el estado de todas las carreras.
UPDATE carreras
SET estado = 'Inactiva';
08 · Quitar filas

DELETE: eliminar datos

DELETE elimina filas, pero conserva la tabla, sus columnas, claves y restricciones.

DELETE FROM carreras
WHERE nombre = 'Carrera de prueba';

Si una carrera tiene alumnos asociados y la FK utiliza ON DELETE RESTRICT, MySQL impide el borrado. La solución no es borrar la relación a la fuerza: primero hay que decidir qué debería ocurrir con esos alumnos.

DELETE sin WHERE: elimina todas las filas de la tabla. La estructura sigue existiendo, pero el contenido desaparece.
-- PELIGRO: elimina todas las filas de carreras.
DELETE FROM carreras;
¿DELETE recupera automáticamente el espacio y reinicia los IDs?
No debe suponerse eso. DELETE elimina filas y no reinicia por sí mismo el contador AUTO_INCREMENT. La administración física del espacio depende del motor y de otras operaciones.
09 · Antes de ejecutar, comprobar

WHERE y un flujo de trabajo seguro

La condición de WHERE es el cinturón de seguridad de UPDATE y DELETE. Hasta estudiar SELECT en profundidad, lo utilizaremos de manera mínima para comprobar qué filas coincide con la misma condición.

Previsualizar

Ejecutar un SELECT con la condición que se piensa usar.

Contar mentalmente

Preguntarse cuántas filas deberían verse afectadas.

Ejecutar y verificar

Aplicar el DML y revisar el número de filas modificadas.

-- 1. Comprobar la fila objetivo.
SELECT *
FROM alumnos
WHERE id_alumno = 1;

-- 2. Reutilizar exactamente la misma condición.
UPDATE alumnos
SET email = 'nuevo.correo@utn.edu.ar'
WHERE id_alumno = 1;
Safe Updates en Workbench: suele estar habilitado para rechazar UPDATE y DELETE considerados inseguros, por ejemplo cuando no usan una clave en WHERE ni un LIMIT. No conviene desactivarlo automáticamente: primero revisar la sentencia.
¿Por qué podría aparecer el error 1175?
Workbench puede estar usando el modo seguro y considerar que la condición no identifica las filas mediante una columna clave. La respuesta correcta suele ser mejorar el WHERE; desactivar la protección debería ser una decisión consciente y temporal.
10 · Qué ocurre con las filas relacionadas

Acciones referenciales: RESTRICT, CASCADE y SET NULL

Cuando se modifica o elimina una clave en la tabla padre, las cláusulas ON UPDATE y ON DELETE establecen qué debe ocurrir con las filas hijas.

RESTRICT

Rechazar la operación

Protege la relación. Es apropiado cuando el padre no debería desaparecer mientras tenga dependencias.

CASCADE

Propagar el cambio

Actualiza o elimina automáticamente las filas hijas relacionadas. Debe reflejar una regla real del negocio.

SET NULL

Conservar la fila hija

Coloca la FK en NULL. Solo es posible si esa columna acepta valores nulos.

Ejemplo: carrera y alumnos

CONSTRAINT fk_alumnos_carreras
    FOREIGN KEY (id_carrera)
    REFERENCES carreras (id_carrera)
    ON UPDATE CASCADE
    ON DELETE RESTRICT
  • Si cambia el ID de la carrera, se actualiza en sus alumnos por ON UPDATE CASCADE.
  • Si se intenta eliminar una carrera que todavía tiene alumnos, la operación se rechaza por ON DELETE RESTRICT.

Ejemplo donde CASCADE puede tener sentido

Una tabla de preferencias puramente dependiente del alumno podría eliminarse junto con él:

CREATE TABLE preferencias_alumno (
    id_alumno BIGINT UNSIGNED PRIMARY KEY,
    recibir_novedades BOOLEAN NOT NULL DEFAULT TRUE,
    tema_interfaz ENUM('Claro', 'Oscuro') NOT NULL DEFAULT 'Claro',
    CONSTRAINT fk_preferencias_alumno
        FOREIGN KEY (id_alumno) REFERENCES alumnos (id_alumno)
        ON UPDATE CASCADE
        ON DELETE CASCADE
) ENGINE = InnoDB;
No existe una acción universalmente mejor. La elección depende del significado de la relación y de si la información hija tiene valor histórico propio.

12 · Una red de seguridad inicial

Primer vistazo a las transacciones

Una transacción permite agrupar varias operaciones. Mientras no se ejecute COMMIT, los cambios DML pueden deshacerse con ROLLBACK en tablas InnoDB.

START TRANSACTIONComienza el bloque controlado.
→
DMLINSERT, UPDATE o DELETE.
→
COMMIT / ROLLBACKConfirmar o deshacer.
START TRANSACTION;

UPDATE alumnos
SET email = 'prueba.temporal@utn.edu.ar'
WHERE id_alumno = 1;

-- Observar el cambio antes de decidir.
SELECT * FROM alumnos WHERE id_alumno = 1;

ROLLBACK;
Para confirmar: reemplazar ROLLBACK por COMMIT. Por defecto MySQL usa autocommit, por lo que una sentencia ejecutada fuera de una transacción explícita queda confirmada automáticamente.
Atención con DDL: sentencias como CREATE, ALTER, DROP y TRUNCATE no se comportan como DML reversible y pueden producir commits implícitos.
13 · Integrar el recorrido

Caso guiado: registrar una inscripción

Vamos a cargar los datos en el orden correcto, crear la inscripción y luego modificar su estado.

1

Crear la carrera y conservar su ID

INSERT INTO carreras (nombre, duracion_anios)
VALUES ('Tecnicatura en Desarrollo de Software', 3);

SET @id_carrera = LAST_INSERT_ID();
2

Crear la materia y conservar su ID

INSERT INTO materias (nombre, carga_horaria)
VALUES ('Laboratorio de Programación', 128);

SET @id_materia = LAST_INSERT_ID();
3

Crear el alumno

INSERT INTO alumnos
    (legajo, dni, apellido, nombre, email, id_carrera)
VALUES
    ('A-2026-15', '46123456', 'Fernández', 'Valentina',
     'valentina.fernandez@ejemplo.edu.ar', @id_carrera);

SET @id_alumno = LAST_INSERT_ID();
4

Crear la comisión

INSERT INTO comisiones
    (id_materia, anio, cuatrimestre, turno)
VALUES
    (@id_materia, 2026, 1, 'Noche');

SET @id_comision = LAST_INSERT_ID();
5

Crear la inscripción usando los IDs reales

INSERT INTO inscripciones
    (id_alumno, id_comision, fecha_inscripcion)
VALUES
    (@id_alumno, @id_comision, '2026-03-12');

SET @id_inscripcion = LAST_INSERT_ID();

Las variables con @ solo guardan temporalmente los IDs en la sesión actual. Se usan aquí como ayuda práctica; su estudio detallado no forma parte del mínimo de esta unidad.

6

Modificar el estado de la inscripción creada

UPDATE inscripciones
SET estado = 'Aprobada'
WHERE id_inscripcion = @id_inscripcion;
La lógica del caso importa más que los números: primero existen los padres, luego los hijos y por último la relación N a N representada por inscripciones.
14 · Patrones que conviene evitar

Errores frecuentes

No nombrar columnas

Hace que el INSERT dependa del orden total de la tabla.

Confundir NULL con texto vacío

Representan situaciones distintas.

Insertar hijos antes que padres

La FK rechaza la referencia inexistente.

Usar IDs inventados

Puede relacionar filas incorrectas o producir errores.

Olvidar WHERE

UPDATE o DELETE afecta todas las filas.

Aplicar CASCADE por comodidad

Puede borrar información histórica de manera no deseada.

Desactivar restricciones

Oculta el problema en vez de corregir los datos.

Probar sobre datos importantes

La práctica debe hacerse en una base controlada o dentro de una transacción.

¿Un mensaje de foreign key significa que MySQL “anda mal”?
No. Generalmente significa que la operación intenta crear una relación imposible o borrar una fila todavía necesaria. Hay que revisar el modelo, el orden de carga y los IDs utilizados.
¿CASCADE es siempre peligroso?
No. Es correcto cuando la fila hija carece de sentido sin su padre. El problema aparece cuando se elige sin analizar qué información se perdería.
15 · Detenerse y comprobar

Preguntas y práctica mínima

Intentá responder antes de desplegar cada solución.

1. ¿Por qué se insertan primero las carreras y después los alumnos?
Porque alumnos.id_carrera es una foreign key y solo puede referenciar una carrera que ya exista.
2. ¿Qué diferencia hay entre omitir estado y escribir NULL?
Al omitirlo se utiliza el DEFAULT si fue definido. Escribir NULL intenta guardar ausencia de valor y falla si la columna es NOT NULL.
3. ¿Qué ocurre si UPDATE no incluye WHERE?
Todas las filas reciben los nuevos valores indicados en SET.
4. ¿Por qué RESTRICT puede impedir borrar una carrera?
Porque existen alumnos que todavía la referencian y el borrado dejaría foreign keys sin una fila padre válida.
5. ¿TRUNCATE es simplemente un DELETE más rápido?
No. Vacía toda la tabla, es DDL, no admite WHERE, produce un commit implícito, reinicia AUTO_INCREMENT y tiene restricciones específicas con foreign keys.

Actividad mínima

  1. Cargar dos carreras y tres materias.
  2. Cargar tres alumnos, dejando un correo en NULL.
  3. Crear dos comisiones y tres inscripciones válidas.
  4. Intentar una inscripción con un alumno inexistente y explicar el error.
  5. Modificar el correo de un alumno usando su PK en WHERE.
  6. Crear una fila de prueba, eliminarla dentro de una transacción y ejecutar ROLLBACK.
  7. Explicar qué ocurriría al intentar borrar una carrera con alumnos asociados.
16 · Cierre

Síntesis de la parte

  • INSERT agrega filas y conviene indicar siempre las columnas.
  • AUTO_INCREMENT, DEFAULT y NULL resuelven situaciones diferentes.
  • Las tablas padre se cargan antes que las tablas hijas.
  • Las restricciones rechazan operaciones que producirían datos inválidos.
  • UPDATE y DELETE requieren una condición precisa cuando no se desea afectar toda la tabla.
  • Las acciones referenciales deben elegirse según el significado de la relación.
  • DELETE, TRUNCATE y DROP no son equivalentes.
  • Una transacción permite confirmar o deshacer DML antes del COMMIT.

Glosario mínimo

DMLSentencias que agregan, modifican o eliminan filas.
Fila padreRegistro que posee la clave referenciada.
Fila hijaRegistro que contiene la foreign key.
RESTRICTImpide una modificación o eliminación que rompería la referencia.
CASCADEPropaga la operación hacia las filas relacionadas.
SET NULLConserva la fila hija y reemplaza la FK por NULL.
TransacciónConjunto de operaciones que se confirma con COMMIT o se deshace con ROLLBACK.
AutocommitModo predeterminado que confirma cada sentencia ejecutada fuera de una transacción explícita.
