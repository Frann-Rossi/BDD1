Unidad 1 · Parte 5 · Implementación con DDL

DDL, tipos de datos y restricciones

En este recorrido vas a transformar un modelo relacional en estructuras reales de MySQL. El objetivo no es memorizar sentencias aisladas: es aprender a tomar decisiones correctas antes de crear una tabla.

Nivel inicialMySQL 8Lectura autónomaCon práctica guiada

Al finalizar vas a poder

  • Distinguir DDL de otras familias de sentencias SQL.
  • Elegir tipos de datos básicos según el significado real de cada dato.
  • Reconocer claves candidatas, primarias, foráneas, simples y compuestas.
  • Crear bases y tablas con restricciones de integridad.
  • Modificar e inspeccionar estructuras desde MySQL Workbench.
01 · Organización del material

¿Dónde se ubica este bloque?

En la planificación 2026, este bloque se estudia después del Modelo Entidad-Relación, la transformación al modelo relacional y la normalización. Aquí se da el paso desde el diseño ya resuelto hacia su implementación en MySQL.

Antes

Problema, reglas del negocio, DER, modelo relacional y normalización.

Ahora

Tipos, claves, restricciones, CREATE, ALTER y DROP.

Después

INSERT, UPDATE, DELETE y consultas con SELECT.

Idea central: un DER no crea nada en el servidor. El DDL es el puente que convierte el diseño en bases, tablas, columnas, claves y restricciones reales.
02 · Familias de SQL

¿Qué es DDL?

DDL significa Data Definition Language o Lenguaje de Definición de Datos. Reúne las sentencias que crean, modifican o eliminan la estructura de una base de datos.

CREATE

Crea bases, tablas y otros objetos.

ALTER

Modifica una estructura existente.

DROP

Elimina un objeto completo.

No debe confundirse con DML, que modifica filas, ni con DQL, que consulta datos.

NecesidadFamiliaEjemplo
Crear una tablaDDLCREATE TABLE
Agregar un alumnoDMLINSERT
Consultar alumnosDQLSELECT
Asignar permisosDCLGRANT

    id_alumno INT PRIMARY KEY
);
03 · Convenciones que evitan problemas

Cómo nombrar bases, tablas y columnas

MySQL admite muchas formas de nombrar objetos, pero una convención estable mejora la lectura y reduce errores.

Minúsculas

Usar gestion_academica, no alternar entre mayúsculas y minúsculas.

Sin espacios

Preferir fecha_nacimiento y evitar Fecha Nacimiento.

Nombres expresivos

id_carrera comunica más que codigo1.

Evitar palabras reservadas: nombres como order, group o select pueden obligar a usar comillas invertidas y generar confusión. Es mejor elegir otro nombre.

04 · Qué puede guardar cada columna

Tipos de datos básicos de MySQL

El tipo de dato limita qué valores puede almacenar una columna y determina cómo se comparan, ordenan y calculan esos valores.

Enteros

TINYINT, SMALLINT, INT y BIGINT.

Para cantidades enteras e identificadores.

Decimales exactos

DECIMAL(p,s)

Ideal para precios, importes y porcentajes que requieren precisión.

Texto breve

CHAR(n) y VARCHAR(n)

CHAR tiene longitud fija; VARCHAR, variable.

Texto extenso

TEXT

Para observaciones o descripciones largas.

Fechas y horas

DATE, TIME, DATETIME y TIMESTAMP.

Elegir según se necesite fecha, hora o ambas.

Lógico

BOOLEAN

En MySQL se interpreta como un alias de un entero pequeño; se usan normalmente TRUE y FALSE.

Lista cerrada

ENUM(...)

Útil cuando hay pocos valores posibles y se espera que cambien muy poco.

Documento flexible

JSON

Valida documentos JSON y permite consultar sus elementos.

Sin signo

UNSIGNED

Evita negativos en tipos numéricos cuando el dominio no los admite.

Para texto nuevo, usar utf8mb4. Permite almacenar el repertorio completo de Unicode. En los ejemplos no utilizaremos el antiguo utf8/utf8mb3.
No escribir INT(11) para indicar “once dígitos”. El número entre paréntesis no limita el rango del entero. En el material nuevo usaremos simplemente INT, BIGINT, etc.
05 · Decidir antes de escribir

Cómo elegir un tipo de dato

Antes de elegir, conviene hacerse cuatro preguntas: ¿se harán cálculos?, ¿puede tener ceros iniciales?, ¿qué tamaño máximo real necesita?, ¿puede faltar?

DatoTipo sugeridoRazonamiento
EdadTINYINT UNSIGNEDEs entera, pequeña y no negativa. Aun mejor: guardar fecha de nacimiento y calcularla.
DNIVARCHAR(15)Es un identificador, no una cantidad para operar.
TeléfonoVARCHAR(25)Puede contener prefijos, signo +, espacios o ceros iniciales.
PrecioDECIMAL(10,2)Necesita precisión exacta; evitar FLOAT para dinero.
Fecha de inscripciónDATENo necesita hora.
Momento exacto de creaciónDATETIME o TIMESTAMPRequiere fecha y hora.
Estado simpleENUM o tablaENUM sirve si la lista es pequeña y estable; una tabla sirve si cambia o tiene más datos.
¿Por qué no usar VARCHAR(255) para todo?
Porque oculta el significado real del dato, dificulta validaciones y puede generar diseños pobres. El tamaño debe surgir de una necesidad razonable, no de “por las dudas”.
¿Por qué no guardar la edad directamente?
Porque cambia con el tiempo. Guardando fecha_nacimiento se conserva un dato estable y la edad puede calcularse cuando sea necesaria.
06 · Identificar y relacionar

Claves e identificadores

Clave candidata

Atributo o conjunto mínimo de atributos capaz de identificar una fila sin repetir.

Clave primaria

Clave candidata elegida como identificador principal. No admite duplicados ni NULL.

Clave alternativa

Otra clave candidata que no fue elegida como primaria; suele protegerse con UNIQUE.

Clave natural

Existe en el dominio real: legajo, CUIT, código oficial.

Clave sustituta

Se crea para identificar: por ejemplo, id_alumno autoincremental.

Clave foránea

Columna que referencia una clave de otra tabla y mantiene la integridad referencial.

CARRERAS
PK id_carrera
nombre
1 ⟶ N
ALUMNOS
PK id_alumno
legajo UNIQUE
FK id_carrera

Por qué preferimos claves sustitutas numéricas

  • Son pequeñas y estables.
  • Simplifican las claves foráneas.
  • No dependen de un dato del negocio que podría cambiar.
  • Facilitan la lectura inicial del modelo.
Convención de la cátedra. Salvo indicación contraria, las tablas usarán una PK sustituta numérica con nombre id_<tabla>, generalmente definida como AUTO_INCREMENT. Los datos naturales o combinaciones que no deben repetirse se protegerán con UNIQUE. Esta decisión busca simplificar la cursada y las FK; no convierte en incorrectas a las claves naturales, textuales o compuestas.

Ejemplo: en inscripciones podemos usar id_inscripcion como PK y, al mismo tiempo, impedir duplicar alumno y comisión:

UNIQUE (id_alumno, id_comision)
07 · Reglas protegidas por el servidor

Restricciones de integridad

Restricción/atributoQué garantizaEjemplo
PRIMARY KEYIdentificación única y no nula.PRIMARY KEY (id_alumno)
FOREIGN KEYLa referencia debe existir en la tabla padre.REFERENCES carreras(id_carrera)
NOT NULLEl dato es obligatorio.apellido VARCHAR(60) NOT NULL
UNIQUENo permite valores repetidos.legajo VARCHAR(20) UNIQUE
CHECKValida una condición lógica.CHECK (duracion_anios BETWEEN 1 AND 8)
DEFAULTAsigna un valor cuando no se informa.estado ENUM(...) DEFAULT 'Activo'
AUTO_INCREMENTGenera una secuencia numérica.id_alumno INT AUTO_INCREMENT
Una restricción no reemplaza el análisis. La base solo puede validar las reglas que nosotros definimos correctamente.
¿DEFAULT puede copiar automáticamente el valor de otra columna?
No es la solución adecuada para ese caso. Si un valor real todavía no se conoce, suele ser mejor dejarlo en NULL y actualizarlo después. Las reglas que dependen de otras columnas requieren analizar si corresponde un CHECK, una columna generada, un trigger o la lógica de la aplicación.
08 · Primer objeto real

Crear y seleccionar una base de datos

1

Crear

CREATE DATABASE IF NOT EXISTS gestion_academica
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_0900_ai_ci;

Las dos últimas líneas indican cómo se almacenará y cómo se comparará el texto de la base:

CHARACTER SET utf8mb4

Define el juego de caracteres. utf8mb4 permite guardar texto Unicode completo: letras con acentos, ñ, símbolos y también emojis.

COLLATE utf8mb4_0900_ai_ci

Define las reglas de comparación y ordenamiento de esos textos. En esta intercalación de MySQL 8, ai significa que no distingue acentos al comparar y ci que no distingue mayúsculas de minúsculas.

Ejemplo sencillo: con esta configuración, al comparar textos, 'MARIA' y 'maria' se consideran equivalentes; del mismo modo, una comparación puede tratar 'José' y 'Jose' como iguales. Esto no modifica lo que fue guardado: define cómo MySQL compara y ordena esos valores.
¿Hay que memorizar utf8mb4_0900_ai_ci?
No. En esta etapa alcanza con comprender la diferencia: CHARACTER SET indica qué caracteres pueden representarse y COLLATE indica cómo se comparan y ordenan. La intercalación elegida es una opción habitual y adecuada para trabajar con MySQL 8.
2

Seleccionar para trabajar

USE gestion_academica;
3

Comprobar

SELECT DATABASE();
SHOW DATABASES;
DROP DATABASE elimina toda la base. No usarlo por costumbre al principio de cada script. Si se incluye para pruebas, debe estar comentado y perfectamente identificado.
09 · Del modelo a MySQL

Crear tablas paso a paso

Primero se crean las tablas que no dependen de otras. Después, las que contienen claves foráneas.

1. Tabla padre: carreras

CREATE TABLE carreras (
    id_carrera INT UNSIGNED AUTO_INCREMENT,
    nombre VARCHAR(100) NOT NULL,
    duracion_anios TINYINT UNSIGNED NOT NULL,
    estado ENUM('Activa', 'Inactiva') NOT NULL DEFAULT 'Activa',

    CONSTRAINT pk_carreras PRIMARY KEY (id_carrera),
    CONSTRAINT uq_carreras_nombre UNIQUE (nombre),
    CONSTRAINT chk_carreras_duracion
        CHECK (duracion_anios BETWEEN 1 AND 8)
) ENGINE = InnoDB;

2. Tabla hija: alumnos

CREATE TABLE alumnos (
    id_alumno BIGINT UNSIGNED AUTO_INCREMENT,
    legajo VARCHAR(20) NOT NULL,
    dni VARCHAR(15) NOT NULL,
    apellido VARCHAR(60) NOT NULL,
    nombre VARCHAR(60) NOT NULL,
    fecha_nacimiento DATE NULL,
    email VARCHAR(120) NULL,
    id_carrera INT UNSIGNED NOT NULL,

    CONSTRAINT pk_alumnos PRIMARY KEY (id_alumno),
    CONSTRAINT uq_alumnos_legajo UNIQUE (legajo),
    CONSTRAINT uq_alumnos_dni UNIQUE (dni),
    CONSTRAINT uq_alumnos_email UNIQUE (email),
    CONSTRAINT fk_alumnos_carreras
        FOREIGN KEY (id_carrera)
        REFERENCES carreras (id_carrera)
        ON UPDATE CASCADE
        ON DELETE RESTRICT
) ENGINE = InnoDB;
Observá la secuencia: columnas primero, restricciones después. Esta forma facilita leer y corregir una tabla cuando recién se está aprendiendo.
¿Por qué dni y legajo no son la PK?
Porque pueden tener reglas externas, formatos variables o cambios administrativos. Se mantienen como claves candidatas protegidas con UNIQUE, mientras id_alumno funciona como identificador interno estable.
10 · Integridad referencial

Foreign keys, relaciones y acciones referenciales

Una clave foránea impide que una fila apunte a un registro inexistente. En InnoDB, MySQL controla esas relaciones.

RESTRICT

Impide borrar la fila padre si todavía está referenciada.

CASCADE

Propaga el borrado o cambio. Debe usarse con intención, no por comodidad.

SET NULL

Deja la FK en NULL; la columna debe admitirlo.

CONSTRAINT fk_alumnos_carreras
    FOREIGN KEY (id_carrera)
    REFERENCES carreras (id_carrera)
    ON UPDATE CASCADE
    ON DELETE RESTRICT
Los tipos deben ser compatibles. Si carreras.id_carrera es INT UNSIGNED, la FK alumnos.id_carrera debe usar un tipo compatible.

Relación N a N con tabla asociativa

CREATE TABLE inscripciones (
    id_inscripcion BIGINT UNSIGNED AUTO_INCREMENT,
    id_alumno BIGINT UNSIGNED NOT NULL,
    id_comision INT UNSIGNED NOT NULL,
    fecha_inscripcion DATE NOT NULL,
    estado ENUM('Activa', 'Baja', 'Aprobada') NOT NULL DEFAULT 'Activa',

    CONSTRAINT pk_inscripciones PRIMARY KEY (id_inscripcion),
    CONSTRAINT uq_inscripciones_alumno_comision
        UNIQUE (id_alumno, id_comision),
    CONSTRAINT fk_inscripciones_alumnos
        FOREIGN KEY (id_alumno) REFERENCES alumnos (id_alumno),
    CONSTRAINT fk_inscripciones_comisiones
        FOREIGN KEY (id_comision) REFERENCES comisiones (id_comision)
) ENGINE = InnoDB;

La PK sustituta identifica la inscripción y la restricción UNIQUE conserva la regla de negocio: el mismo alumno no puede inscribirse dos veces en la misma comisión.

11 · Cambiar sin recrear

Modificar tablas con ALTER TABLE

ALTER TABLE permite cambiar la estructura de una tabla que ya existe. Puede utilizarse para agregar, modificar, renombrar o quitar columnas y también para agregar o eliminar restricciones.

Idea básica: primero se indica qué tabla se quiere modificar y después la operación que se realizará sobre ella.
ALTER TABLE nombre_tabla
operacion;

1. Agregar una columna — ADD COLUMN

Agregar una nueva columna indicando su nombre, tipo y restricciones.

ALTER TABLE alumnos
ADD COLUMN telefono VARCHAR(25) NULL;

La palabra COLUMN es opcional en MySQL, pero utilizarla hace más evidente que se está trabajando con una columna.

2. Modificar la definición de una columna — MODIFY COLUMN

MODIFY COLUMN permite cambiar el tipo, tamaño, obligatoriedad, valor por defecto u otras características de una columna sin cambiar su nombre.

ALTER TABLE alumnos
MODIFY COLUMN telefono VARCHAR(40) NOT NULL;
Importante: con MODIFY COLUMN conviene escribir la definición completa que debe conservar la columna. Si ya existen datos incompatibles con el nuevo tipo o con NOT NULL, la modificación puede fallar.

3. Renombrar una columna — RENAME COLUMN

Si solo se desea cambiar el nombre de la columna, MySQL permite hacerlo sin redefinir su tipo.

ALTER TABLE alumnos
RENAME COLUMN telefono TO telefono_contacto;

4. Cambiar nombre y definición — CHANGE COLUMN

CHANGE COLUMN permite renombrar una columna y, al mismo tiempo, volver a definirla. A diferencia de RENAME COLUMN, aquí es obligatorio indicar nuevamente su tipo.

ALTER TABLE alumnos
CHANGE COLUMN telefono_contacto celular VARCHAR(30) NULL;

5. Eliminar una columna — DROP COLUMN

ALTER TABLE alumnos
DROP COLUMN celular;
Atención: eliminar una columna también elimina los datos almacenados en ella. En una base real, esta decisión debe revisarse antes de ejecutarse.

6. Agregar restricciones a una tabla existente

Las restricciones no tienen que definirse obligatoriamente dentro del CREATE TABLE. También pueden agregarse después.

Agregar UNIQUE

ALTER TABLE alumnos
ADD CONSTRAINT uq_alumnos_email
UNIQUE (email);

Agregar CHECK

ALTER TABLE alumnos
ADD CONSTRAINT chk_alumnos_email
CHECK (email IS NULL OR email LIKE '%@%');

Agregar una clave foránea

Primero debe existir la columna que actuará como FK y su tipo debe ser compatible con la PK referenciada.

ALTER TABLE alumnos
ADD CONSTRAINT fk_alumnos_carreras
FOREIGN KEY (id_carrera)
REFERENCES carreras (id_carrera)
ON UPDATE CASCADE
ON DELETE RESTRICT;

7. Eliminar restricciones

En MySQL la sintaxis depende del tipo de restricción. No todas se eliminan con la misma palabra.

Qué se desea quitarEjemplo
Clave foráneaALTER TABLE alumnos DROP FOREIGN KEY fk_alumnos_carreras;
Restricción UNIQUEALTER TABLE alumnos DROP INDEX uq_alumnos_email;
Restricción CHECKALTER TABLE alumnos DROP CHECK chk_alumnos_email;
Clave primariaALTER TABLE alumnos DROP PRIMARY KEY;
¿Por qué UNIQUE se elimina con DROP INDEX? En MySQL, una restricción UNIQUE se implementa mediante un índice único. Por eso, para quitar esa restricción se elimina el índice correspondiente.

8. Cambiar una restricción existente

Muchas restricciones no se “editan” directamente. La estrategia habitual consiste en eliminar la definición anterior y crear una nueva. Por ejemplo, cambiar una FK de ON DELETE RESTRICT a ON DELETE CASCADE:

ALTER TABLE alumnos
DROP FOREIGN KEY fk_alumnos_carreras;

ALTER TABLE alumnos
ADD CONSTRAINT fk_alumnos_carreras
FOREIGN KEY (id_carrera)
REFERENCES carreras (id_carrera)
ON UPDATE CASCADE
ON DELETE CASCADE;

9. Cambiar o quitar un valor DEFAULT

Definir DEFAULT

ALTER TABLE carreras
ALTER COLUMN estado SET DEFAULT 'Activa';

Quitar DEFAULT

ALTER TABLE carreras
ALTER COLUMN estado DROP DEFAULT;

10. Verificar cómo quedó la tabla

Después de modificar una estructura conviene inspeccionarla.

Vista rápida

DESCRIBE alumnos;

Definición completa

SHOW CREATE TABLE alumnos;
Resumen práctico: ADD agrega, MODIFY redefine, RENAME cambia el nombre, CHANGE puede cambiar nombre y definición, y DROP elimina. Con restricciones, recordar que a veces primero hay que quitar la anterior y luego agregar la nueva.
12 · Operaciones destructivas

DROP, TRUNCATE y DELETE no son lo mismo

SentenciaQué eliminaConserva la tablaFamilia
DROP TABLEEstructura y datosNoDDL
TRUNCATE TABLETodas las filasSíDDL
DELETEFilas seleccionadas o todasSíDML
DROP TABLE IF EXISTS alumnos;
TRUNCATE TABLE alumnos;
No ejecutar para “probar”. Antes de una operación destructiva, leer la sentencia completa, confirmar la conexión y verificar en qué base se está trabajando.

14 · Tipo especial de MySQL

Primer vistazo al tipo JSON

MySQL posee un tipo JSON nativo. No reemplaza el modelo relacional: sirve para datos flexibles que no justifican nuevas columnas o tablas en ese momento.

CREATE TABLE configuraciones_alumno (
    id_configuracion BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    id_alumno BIGINT UNSIGNED NOT NULL,
    preferencias JSON NOT NULL,
    CONSTRAINT fk_configuraciones_alumno
        FOREIGN KEY (id_alumno) REFERENCES alumnos (id_alumno)
);

Buen uso inicial

Preferencias opcionales o configuraciones con estructura flexible.

Mal uso

Guardar carreras, materias o inscripciones completas dentro de un JSON para evitar diseñar relaciones.

Alcance de este documento: acá solo reconocemos el tipo. La inserción y consulta de documentos JSON se trabajará con DML y SELECT.
15 · Lo que suele salir mal

Errores frecuentes y cómo pensarlos

Crear la tabla hija primero

La tabla referenciada todavía no existe. Crear primero las tablas padre.

Tipos incompatibles en PK y FK

INT y INT UNSIGNED no deben mezclarse sin revisar compatibilidad.

Usar número para teléfonos o DNI

Son identificadores y pueden tener formato, prefijos o ceros iniciales.

Olvidar una regla UNIQUE

Una PK sustituta no evita que se repita un legajo, DNI o par alumno-comisión.

CHECK invertido

La condición debe leerse en palabras. Por ejemplo: cantidad_real <= cantidad_reservada.

DEFAULT para una regla compleja

Un valor por defecto no es un reemplazo universal para lógica entre columnas.

Usar utf8 antiguo

En material nuevo preferimos utf8mb4.

Copiar sintaxis de otro gestor

IDENTITY es de SQL Server; en MySQL usamos AUTO_INCREMENT.

16 · Comprobar antes de seguir

Preguntas y micropráctica

1. ¿Un DNI debería ser INT?
No necesariamente. Aunque tenga dígitos, funciona como identificador y no se usa para cálculos; VARCHAR suele ser más adecuado.
2. ¿Toda clave candidata debe ser PRIMARY KEY?
No. Se elige una como PK y las demás pueden protegerse con UNIQUE.
3. ¿Una FK puede apuntar a una fila inexistente?
No, salvo que la FK admita NULL y el valor almacenado sea precisamente NULL.
4. ¿AUTO_INCREMENT garantiza una regla del negocio?
Solo genera identificadores. Las reglas como “legajo no repetido” necesitan restricciones adicionales.
5. ¿DROP TABLE borra solamente las filas?
No. Elimina la tabla completa, incluida su estructura.
6. ¿ENUM siempre es la mejor opción?
No. Es práctico para listas pequeñas y estables; si los valores cambian o tienen atributos propios, conviene una tabla.

17 · Cierre

Síntesis

  • DDL define la estructura; DML modifica filas; SELECT consulta.
  • El tipo de dato se elige por significado, operaciones, formato y tamaño real.
  • Una PK identifica; una FK relaciona; UNIQUE protege otras claves candidatas.
  • Las claves sustitutas numéricas simplifican el modelo, pero no eliminan las reglas del negocio.
  • Las restricciones hacen que el servidor rechace datos incompatibles.
  • Las tablas padre se crean antes que las tablas hijas.
  • ALTER modifica; DROP elimina; TRUNCATE vacía una tabla.
  • JSON complementa el modelo relacional, no lo reemplaza.
